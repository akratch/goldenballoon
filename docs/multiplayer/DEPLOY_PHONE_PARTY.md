# Deploy Phone Party

This is the short path: three commands, one value to fill in, and a
verification that pairs a synthetic phone for you. The deep runbook with the
compatibility, migration and canary rules lives in
[docs/ops/multiplayer/deploy.md](../ops/multiplayer/deploy.md); this page does
not repeat it.

## The three commands

```sh
npx wrangler login
tools/deploy_party.sh
python3 tools/verify_party_deploy.py --origin https://YOUR-PARTY-HOST
```

`tools/deploy_party.sh` prints the exact verify command with your host already
filled in, so you can copy it from the deploy output.

Before the first real deploy, run `tools/deploy_party.sh --dry-run`. It does
everything except the mutation, needs no Cloudflare account, and tells you
what is missing.

## The one value you fill in

```sh
cp services/party/ops/production.env.example services/party/ops/production.env
$EDITOR services/party/ops/production.env      # set PARTY_DOMAIN=party.example.com
```

`PARTY_DOMAIN` is a bare hostname — no scheme, no port, no path. It is the
only deployment value you edit. `tools/deploy_party.sh` threads it into both
the Wrangler custom-domain route and `PARTY_ORIGIN`, generating the untracked
`services/party/wrangler.production.jsonc` from the tracked
`services/party/wrangler.jsonc`. The two can therefore never disagree — and if
they did, the service refuses every request, because `PARTY_ORIGIN` is the
browser-origin authority boundary.

The tracked config keeps `party.example.invalid` as its default. `.invalid` can
never resolve, so an unconfigured checkout is not deployable. Do not edit that
placeholder in place: `tests/check_party_production_config.py` requires it to
survive in the tracked file, and requires it to be *gone* from the generated
file, and `tools/deploy_party.sh` runs both directions before it will deploy.

## The two secrets

Neither secret is ever a file, a Wrangler var, a command-line argument or
anything the deploy script reads. Provision them once, interactively, so the
value is typed into a prompt and never enters your shell history:

```sh
cd services/party
npx wrangler secret put PARTY_HMAC_KEY  --config wrangler.production.jsonc --env production
npx wrangler secret put OPS_READ_TOKEN  --config wrangler.production.jsonc --env production
```

(`wrangler.production.jsonc` is generated by the first `tools/deploy_party.sh
--dry-run`, so run that before setting secrets.)

- **`PARTY_HMAC_KEY`** — at least 32 random bytes, e.g.
  `openssl rand -base64 48`. Every invite, fallback code, host credential and
  controller credential is derived from it. Rotating it invalidates all of
  them at once; see the rotation/room-drain procedure in the deep runbook
  before you ever do that.
- **`OPS_READ_TOKEN`** — an independent random secret of at least 32
  characters. It only reads `/api/ops/capacity` and `/api/ops/health`. It must
  never be the same value as the HMAC key.

`tools/deploy_party.sh` checks that both **names** exist in the secret store
and stops with these instructions if either is missing. It never reads a value.

## DNS, the custom domain, and why TLS is not optional

The production environment binds one **custom-domain** route, which is what
provisions a certificate for `PARTY_DOMAIN`. A `*.workers.dev` host is
explicitly disabled (`workers_dev: false`, `preview_urls: false`) in both
environments, so there is exactly one origin to trust.

Requirements you must satisfy in the Cloudflare dashboard before deploying:

- `PARTY_DOMAIN` is on a zone in the same account as the Worker.
- Nothing else already serves that hostname (a custom-domain route takes it
  over entirely — it serves the static launcher, `/controller/`, `/room/` and
  `/api/` from one origin).

TLS is mandatory, not a preference:

- a phone joins by **scanning a QR code**; iOS and Android will not open a
  camera-sourced insecure URL into a usable pad, and the controller page needs
  a secure context for `crypto.subtle`, which derives the pairing phrase;
- signaling runs over **WSS**, which browsers only allow from a secure page;
- the service's own `validPartyOrigin()` accepts `http:` **only** for
  loopback development, and refuses everything else with a 503 before it
  touches any Durable Object.

## Point the launcher at the deployed origin

The native launcher compiles its Party origin in. `MDKR_PARTY_ORIGIN`
(CMakeLists.txt:199) must be **byte-identical** to the deployed
`https://PARTY_DOMAIN` — same scheme, no trailing slash — or the QR code the
launcher draws will point somewhere that cannot pair.

```sh
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release \
      -DMDKR_PARTY_ORIGIN=https://YOUR-PARTY-HOST
cmake --build build/release
```

CMake refuses any value that does not begin with `https://`. Leaving it empty
builds a launcher with Phone Party unaddressed — that is the correct default
for a build that is not for your deployment. Such a build shows **no Phone
Party surface at all** (`PhoneParty_availableInBuild`): no launcher card, no
in-game overlay entry. It is not a degraded feature, it is an absent one.

Order matters: deploy and verify the service first, then build the release
against the verified origin. A build compiled against the placeholder origin
cannot pair and must not be shipped.

### Releases must be built pointing at the deployed origin

The value is compiled in, so it is a property of the **artifact**, not of the
machine that runs it. A release built without it ships without Phone Party,
silently and irreversibly — no runtime setting recovers it.

Two repository variables drive the release lanes (Settings → Secrets and
variables → Actions → Variables — plain variables, not secrets; the origin is
public by construction, it is printed on the player's own screen as a QR code):

| Variable | Value | Meaning |
| --- | --- | --- |
| `MDKR_PARTY_ORIGIN` | `https://PARTY_DOMAIN` | Compiled into every packaged artifact. |
| `MDKR_ALLOW_PARTYLESS_RELEASE` | `1` | Deliberate escape hatch: ship with Phone Party absent. |

**How the guard behaves.** `.github/workflows/release.yml` (the `validate`
job) and `.github/workflows/macos-release.yml` (the `party` step, before any
build tool is installed) fail the run before anything is compiled unless
either:

- `MDKR_PARTY_ORIGIN` is set and is exactly `https://HOST[:PORT]` — no
  trailing slash, path, query, fragment or embedded credentials, and not a
  reserved placeholder host (`*.invalid`, `*.example`, `example.com`,
  `localhost`); or
- `MDKR_ALLOW_PARTYLESS_RELEASE` is exactly `1`, in which case the run
  continues and prints a loud banner recording that these artifacts ship with
  Phone Party unavailable. That escape hatch exists so an unrelated release is
  never blocked, but it is a deliberate, logged choice — never a default.

The resolved origin is a job output that every build lane consumes:
`release.yml` threads it into both the Linux and the Windows
`cmake -B build …` configure, and `macos-release.yml` passes it to
`macos/Scripts/build_app_bundle.sh --party-origin`, which forwards it as
`-DMDKR_PARTY_ORIGIN`. Empty stays legal everywhere — that is the partyless
path — so nothing defaults it to a placeholder.

**One origin, verified once.** The origin compiled into the artifact and the
origin `tools/verify_party_deploy.py` passed against must be the *same string*.
Verifying `https://party.example.com` and then shipping a build compiled
against anything else — a staging host, a trailing slash, a stale variable —
means nothing was verified about what players actually run.

**What the release lanes prove.** `release.yml`'s Linux job launches the real
launcher (built tree and extracted package) under xvfb with
`MDKR_APP_PARTY_TRACE=1`, which makes the Phone Party surface draw without a
ROM and emit exactly one line from inside the draw itself:

```
[app] party: origin=https://PARTY_DOMAIN transport=available phase=closed invite=0 qr=0 code=0
```

The lane asserts the line appears exactly once, that `origin=` equals the
origin this artifact was built with (`unset` on the partyless path — the
expected value is fixed per run, never "either"), and that
`transport=available`. That proves the surface committed draws and that the
compiled origin and the linked native WSS/WebRTC transport reached the shipped
binary. It does **not** prove pairing: with no network and no ROM the phase is
`closed` and `invite`/`qr`/`code` are `0`. Live pairing is what
`tools/verify_party_deploy.py` proves, against the same origin. The macOS lane
has no AppHost launch, so it carries the guard and the compiled origin but no
drawn-surface witness.

## The edge rate-limit rule

`services/party/ops/free-rate-limit-rule.json` is the reviewed payload: one
enabled block rule, matching `/api/` only, 30 requests per 10 seconds per
IP+colo, 10-second mitigation. Apply it to the zone's `http_ratelimit`
entry-point ruleset through the Rulesets API with a least-privilege
`Zone WAF Write` token.

**A Free plan allows exactly one rule.** Export the existing ruleset first.

- If the zone has no rate-limit rule, install this payload as-is.
- If the zone already uses its one free rule for something else, **stop**.
  Do not delete, merge or overwrite it. That is an owner decision about which
  protection the zone gets, and the deep runbook treats it as a hard stop.

Deploying without the rule is safe but unprotected: the Worker's own $0
admission budget still fails closed, so the service cannot generate a bill —
it will simply refuse new rooms sooner under abuse. The rule keeps abusive
`/api/` traffic from consuming that budget at all. It never touches `/`,
`/controller/`, `/room/` or any static asset, and
`tools/verify_party_deploy.py` proves that by bursting the controller page
past the rule's threshold and requiring every response to stay 200.

## Verify

```sh
python3 tools/verify_party_deploy.py --origin https://YOUR-PARTY-HOST
```

It exits nonzero on any failure and prints one `PASS`/`FAIL` verdict with an
evidence block. Without a phone, it:

- loads `/` and `/controller/` over TLS and requires 200, the right
  content-type, CSP, Permissions-Policy, HSTS, `nosniff` and `no-referrer`,
  and fetches every script and stylesheet the controller page references;
- checks `/controller` resolves to `/controller/`, that an unknown path is
  refused rather than rewritten into a page, and that `/api/` is Worker-served
  and not shadowed by static assets;
- creates a room, redeems the invite, and completes the **WSS** handshake as a
  synthetic host and controller — offer, answer and ICE envelopes round-trip
  with the phone identity stamped by the service, and a claimed identity is
  overwritten;
- pairs with the six-digit fallback code, rotates the invite, and requires the
  old link *and* the old code to stop working while the new pair works;
- requires every credential response to be `no-store`, cross-origin,
  `null`-origin and origin-less API requests to be refused 403, and no
  `workers.dev` host to be published;
- requires the deployed static build to be the local `dist/web` build.

To prove the verifier itself without any Cloudflare account, run it against a
real local Worker:

```sh
python3 tools/verify_party_deploy.py --self-test
```

That runs `wrangler dev --local` and performs every check above except the
TLS-only assertions, which it reports as skipped.

## Rollback

Wrangler keeps previous versions addressable:

```sh
cd services/party
npx wrangler deployments list --config wrangler.production.jsonc --env production
npx wrangler rollback --config wrangler.production.jsonc --env production
```

Cloudflare does not roll back stored Durable Object data, and forbids rollback
across a class lifecycle migration. Because a first deployment applies the
`v1`/`v2`/`v3` migrations together, the safe rollback target after the first
deploy is a Worker version, not a schema. Read the version-skew section of
[docs/ops/multiplayer/deploy.md](../ops/multiplayer/deploy.md) before rolling
back anything that changed a migration.

To take Phone Party down without a code change, set the admission kill switch:

```sh
cd services/party
npx wrangler deploy --config wrangler.production.jsonc --env production \
    --var MAX_ADMISSIONS_PER_DAY:0
```

A literal zero refuses every new room and join with a typed
`service_budget_safe` while leaving established rooms on their control
reserve. Restore by redeploying without the override.

## Stop conditions

Stop and enter [rollback](../ops/multiplayer/rollback.md) rather than pressing
on if any of these appear:

- a secret, room name, invite, fallback code or player name shows up in any
  log, response body or dashboard field;
- a binding appears in the deploy output that is not one of the four Durable
  Objects and three vars;
- any billing method or paid-overage path becomes attached to the account;
- `/api/ops/capacity` shows admission climbing without matching pairings, or
  the control reserve is exhausted;
- an old invite or old fallback code still pairs after a rotation;
- `tools/verify_party_deploy.py` fails for any reason on the deployed origin.

## What still requires a human

Nothing on this page can be automated away, and the deploy script does not
pretend otherwise:

1. **Cloudflare account provisioning** — creating the account, choosing the
   plan, and confirming no billing method is attached.
2. **DNS and the zone** — owning `PARTY_DOMAIN`, having its zone in the same
   account, and confirming nothing else serves that hostname.
3. **`wrangler login`** — an interactive browser authorization.
4. **Setting the two secrets** — interactive prompts, by design.
5. **The one free WAF rule** — if the zone already spends it, deciding what to
   do is an owner call, not a script's.
6. **Building and shipping the release** compiled against the verified origin.
